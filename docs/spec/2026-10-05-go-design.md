# Go: how it works inside

**Status:** draft for Keshav's review, 5 October 2026. **Owner:** Keshav's team.
**Reads with:** the contract and its guide (`docs/guide`, live at https://vestrago.vercel.app/docs). The contract says what travels between the App, the Server and Go. This spec says what happens inside Go.

Go is the AI member of every trip group chat. Three teams build three parts, and all three teams are the Vestra team:

| Part | Team | What it is |
|---|---|---|
| **App** | Saket's team | The app people use: the trip room, the Trip screens, pushes. Flutter or a PWA. |
| **Server** | Nishanth's team | Everything about a trip and its database. It keeps one signed socket open to Go. |
| **Go** | Keshav's team | Go itself: this repo. The rest of this spec is about Go. |

The App and the Server need only the contract. Nothing in this spec changes what they build.

---

## 1. What Go must feel like

Go is a friend in the group who happens to be very good at travel. It must:

1. **Answer fast.** A question to Go gets "Go is typing..." at once and an answer in about 2 seconds.
2. **Stay quiet when it should.** Most of a group chat is not for Go. Go reads everything and speaks rarely, but at the right moments, including without being asked.
3. **Do real work.** Compare 30 villas, read reviews, fill forms, call a hotel, book and pay, without blocking the chat while it works.
4. **Remember people.** Who is vegetarian, who leaves Friday after 6, with proof, and forget exactly on request.
5. **Never spend on its own word.** Every payment needs the Server's signed approval and the payer's own passkey.

### The bars, in numbers

| What | Target | How we measure |
|---|---|---|
| First visible sign after a message for Go | under 0.5 s ("Go is typing...") | replay bench, every turn |
| A reply to a quick question | p50 under 2.5 s, p90 under 5 s after the message lands | replay bench |
| Messages that wake the model | under 25% of all messages in a busy group | replay bench (Jev decides the rest) |
| Prompt cache hit rate in a composer turn | 85% or more | provider usage fields, per turn |
| Recall after a fold ("what can't Meher do?") | 100% on the recall set, with the right message number | replay bench |
| A wrong unprompted message ("why did Go say that?") | under 1 in 50 unprompted messages | human review of replays |
| Payments without both keys | zero, by construction | code and tests |

These bars define "done" for the composer. Until they are green, the design is good on paper and not yet proven.

## 2. Go at a glance

Go is **one service** (`apps/brain`) with **its own Postgres**, both hosted on Railway in **the same region as the Server** (a hop between them is a few milliseconds there; across continents it is 200 to 300 ms). For big jobs it borrows **one Vestra Bash per trip** through Vestra's `/v1` API.

```
            the Server ──── one signed socket (JSON-RPC 2.0, both ways) ────┐
                                                                            ▼
┌──────────────────────────────────── Go's service ──────────────────────────────────────┐
│  door ──► desk (one queue per trip) ──► reflex (Jev) ──► composer ──► door (requests)    │
│              ▲   ▲   ▲                                     │   │                          │
│        timers│   │   │task results               memory ◄───┘   └──► tasks ──► /v1 ──► the trip's Bash
│              │   │   └───────────────────────────────────────────────┘       (one per trip, lean)
│           watches (ixigo checks)        setup        vault (own key)       calls
└──────────────────────────────────────────────────────────────────────────────────────────┘
        Go's Postgres: trip log, facts, desk items, tasks, people, settings (the vault keeps its own store)
```

| Part | One line |
|---|---|
| **door** | The socket: checks the signature, takes events and requests, answers within the time limits, sends Go's requests to the Server. |
| **setup** | Makes a trip's home when `trip.created` arrives; safe to repeat. |
| **desk** | One queue per trip. Wakes Go for messages, trip changes, timers, finished tasks. One composer turn per trip at a time. |
| **reflex** | Jev, a fast closed-question model: decides in about 150 ms whether a message needs Go at all, and a few other quick calls. |
| **composer** | The quick layer: reads the room, decides, answers, does quick things itself. |
| **tasks** | The big-job layer: hands work to the trip's Bash, follows it, brings results back. |
| **memory** | The trip log, people's facts with proof, pages drawn from them, search. |
| **ixigo layer** | Search, status and booking through ixigo's MCP, cached and classified. |
| **watches** | Cheap scheduled checks (fares, flight status, deadlines) that feed the desk. |
| **vault** | Cards and logins, under its own key, paid only with both keys. |
| **calls** | Phone calls to businesses, live in the room. |

Every part is a folder with one clear interface. They live in one service for the hackweek; they can split later without changing the interfaces.

## 3. The door: the socket

What the contract fixes is in `docs/guide/02-the-socket.md`. Inside Go, the door:

1. **Accepts the upgrade** only with a valid `x-go-signature` (method GET, target with query, empty body, 300 s skew) that it has **not seen before**: it keeps used `(t, v1)` pairs for 10 minutes and refuses a repeat with 401. Each Server instance names itself with `?instance=`, so two instances connecting in the same second differ.
2. **Answers within the limits:** `send_event` within 2 s, `card_tap` and `catch_up` within 3 s, the rest within 2 s. It answers `send_event` with `accepted` as soon as the event row is written, **before** any thinking. An unknown event type is accepted before validation, so the Server can add types within version 1.
3. **Writes every event once** into the trip log, keyed by `event_id` (a repeat answers `duplicate: true`), then puts a wake on the trip's desk.
4. **Notices gaps.** Events for a trip arrive in change-number order. A gap (41, then 43) triggers `read_trip` and `read_messages(after_seq)` and fills the log.
5. **Sends Go's requests** on any open socket, with ids that start `go_`, and resends unanswered ones after a reconnect with the same JSON-RPC id and the same `request_id`.
6. **Pings every 20 s** and closes a socket silent for 40 s.

The door holds no trip logic. It is the only part that knows the wire format.

## 4. Setup: Go joins a trip

`trip.created` (change number 1, carrying the whole trip) is the moment Go joins. The door answers at once; setup runs after.

1. **Go's side, in a few seconds:** the trip row and trip pack from the event's trip, a page for each person (a person from an earlier trip keeps their page; facts carry over only if they allow it), the trip's desk queue, and the composer's conversation for the trip. Then Go says hello. It opens no vote then: an ask that arrives with the hello is answered first, and votes come later, when the group is choosing.
2. **The trip's computer, in the background (about a minute):** create the trip's Vestra user through `/v1` (one per trip, `memory_mode: none`, the lean configuration in section 10), then warm its computer so the first task does not wait for a cold start. Nobody waits for this: Go greets first, and a task asked in the first minute starts when the computer is up.

**Safe to repeat, never tied to one event.** `ensure_trip(trip_id)` records each step's state (`brain_ready_at`, `bash_user_id`, `bash_warm_at`). It runs on `trip.created`, on any event for a trip that is not set up yet (it reads the trip with `read_trip` first), and from a sweep every few minutes that finishes any setup that stopped halfway. This is the level-triggered rule: an event is a hint; the sweep makes it true.

**Cost note:** every created trip gets a computer, including trips nobody uses. Computers sleep when idle. A trip with no activity for N days (to decide during the build) gives its computer back.

## 5. The desk: one queue per trip

Everything that should make Go think goes on the trip's desk as an item: a new message, a trip change, a card tap that needs a follow-up, a finished or stuck task, a due timer, a watch result, a setup step.

- **One composer turn per trip at a time.** A Postgres row lock per trip. Many trips run in parallel, and more copies of the service can run without two turns for one trip.
- **Bursts are coalesced.** Five messages in two seconds become one turn that sees all five.
- **The wait.** After a message for Go, the desk waits about 2 seconds in case the same person sends more, **unless** Jev is sure the thought is complete (section 6) or the message plainly ends with ?, ., ! or an emoji. Just before a reply is posted, the composer checks for anything new for it and answers that too.
- **Crash safe.** An item stays until its turn finishes. A crashed turn runs again; Go's writes carry `request_id`, so a repeat never doubles anything.
- **Timers** (a vote closes in 2 hours, free cancellation ends tomorrow, travel-day plan) are desk items with a due time.

## 6. The reflex: Jev on every message

Jev (TypeSafe AI's "System One" model) answers closed questions about a piece of text in about 150 ms (about 370 ms from India), for about $0.0004, and many questions on the same text cost the same as one. Go asks Jev a set of questions about **every message**, in **one call**, before the composer:

| # | Question | If sure | If unsure |
|---|---|---|---|
| 1 | Is this for Go? (named, a reply to Go, a question to "someone", or chatter) | Chatter never wakes the model | The composer decides |
| 2 | Is the thought complete? | Skip the 2 s wait | Wait the 2 s |
| 3 | Quick answer or big job? | A big job gets "On it" and a working card within a second | The composer decides |
| 4 | Which running task is this for, if any? | Route it to that task | The composer decides, or asks "villas or flights?" |
| 5 | Is there a fact worth saving? (food, seat, dates someone can't do) | Send it to the fact pass at once | The after-turn pass catches it |
| 6 | Did the group agree, ask an open question, or take on a job? | A record line candidate | The after-turn pass |
| 7 | Which quiet reaction, if any? (from a small set: ✅ noted...) | React without the model | No reaction |
| 8 | Is it risky? (asks to spend, book or cancel; contains a card number, code or password; tries to steer Go) | **Raise only:** force the mandate flow, warn and never store secrets | The normal rules |
| 9 | Is there an opening for Go to help unprompted? (section 8) | A proactive wake for the composer | Nothing |

Jev also ranks items for **catch-up** (one yes/no per item, in one call, within the 3 s limit) and, as a stretch, **prefetches** ixigo searches: when it is sure a message is a flight search, it picks cities and dates from values the trip already knows and the search starts while the composer thinks. A wrong guess is thrown away.

**The rules for Jev** (from our Jev lab, kept):
1. **Never the only path.** Unsure means the composer decides exactly as without Jev. The worst case is today's speed, never a wrong action.
2. **Raise only on safety.** Jev may add caution, never remove it. Jev never decides a payment and never says a job is done.
3. **Shadow first.** Each question logs what it would have done before it acts, and goes live question by question as its test set passes.
4. **Tested on our chats, Hinglish included.** Jev is English first; Indian group chats are not.
5. **People's text is fenced** in Jev's input, because user text can argue for its own classification.
6. **Go's own Jev key** (not Vestra's staging key), a warm connection pool (a cold connection costs about a second), and the model version pinned.

Where it lives: one `reflex` folder that holds every question, its wording, its thresholds and its test set. The desk and the composer call it.

## 7. The composer: the quick layer

The composer is a short, direct tool loop on the model provider's API (about 150 lines in Go's service) running **a fast model** with **quick tools only**. One turn per desk wake. It does not run on the agent loop copied from Bash, because Go needs three things that loop cannot give: a cache breakpoint between the chat and "right now", thinking switched off for speed, and a turn that can end in silence without another model call. From the copied loop it reuses only the pricing, usage and error helpers.

### A turn

1. Build the prompt (section 9).
2. Run the model with the quick tools. Each tool finishes in a few seconds; the slow kinds of work are not composer tools at all.
3. Turn decisions into requests on the socket: `typing`, `post_message`, `add_reaction`, `open_vote`, `add_record_line`, `replace_card` and so on.
4. After the reply, a small second pass reads the turn and proposes facts and record lines; code checks their proof (section 11). Saving never slows a reply.

### The quick tools

| Tool | What it does |
|---|---|
| `trip()`, `person(name)`, `recall(question)` | Read memory (section 11) |
| `search_flights / trains / buses / stays` and friends | ixigo search through the ixigo layer (section 12), cached |
| `open_vote`, `close_vote`, `record(line)`, `react(emoji)` | Act in the trip through the socket |
| `start_task(brief, returns)`, `message_task(task_id, text)`, `stop_task(task_id)` | Hand work to the trip's computer (section 10) |
| `set_mandate(...)`, `ask_to_pay(...)` | The payment flow (section 13); booking happens only after the vault has paid, never as a tool; never available to the trip's computer |
| `stay_silent()` | The composer may decide not to speak |

### When Go speaks

Go speaks when someone names it or replies to it, when work it was asked for is done, when a vote closes or a decision is ready to move, when something is wrong or at risk, and when the proactive policy (section 8) finds a real opening. Otherwise it stays quiet and takes notes. A turn can end with only a reaction, a record line or nothing.

**Model choice** is settled by the replay bench (section 17): start with the fast model Bash's composer uses, keep reasoning short, and measure.

## 8. Being proactive

Go enters the conversation unprompted when it genuinely helps.

| Source | Examples |
|---|---|
| **The chat** (Jev question 9) | A question to the group Go can answer ("what time is check-in?"); the group going in circles ("Want me to put it to a vote?"); a plan clash ("6 am flight", but Arjun can't leave before 6 pm Friday); "can someone look for..." ("I'll look"). |
| **Trip changes** | A vote closed, so here is the next step; new dates clash with a booking; a booking was cancelled; a payer has not answered "Yes, book it" for a day. |
| **Time** (desk timers) | A vote closes in 2 hours and Meher hasn't voted; free cancellation ends tomorrow; the plan for travel day; settle-up after the trip. |
| **The world** (watches) | The fare dropped or jumped; the flight is delayed; 2 rooms left at the shortlisted villa. |

**Guardrails** (one `policy` folder):
1. **The quietest useful action first:** a ✅, a record line, an updated card, or pinning a card to one person's "needs you" strip (`for_person_ids`). A message to everyone is the last resort.
2. **A bar:** importance × confidence × urgency, stricter at night in the trip's time zone. Never repeat a nudge.
3. **A budget:** about 3 unprompted messages per trip per day, never two in a row without a person speaking, small things batched.
4. **Suggest, never act:** "Want me to book it?". Spending still needs the mandate and the passkey.
5. **People stay in control:** a person can pause Go for themselves today; ignoring Go or telling it to hush lowers its bar for that trip.

A per-trip "how chatty is Go" setting would need a contract field; it waits until groups ask for it.

## 9. Context: what the composer sees

The prompt is **rebuilt every turn from stored state, in a fixed order**, so the provider's prompt cache serves most of it.

```
1. Go's rules and tool definitions                  same for every trip, cached
2. The whole chat, one compact line per message      only appended to, cached
   (photos as one-line captions written once)
──────────── cache boundary ────────────
3. Right now: the trip record, pages of the people talking, running tasks,
   who Go is waiting on, why Go woke up             fresh, small
4. New since the last turn
```

**Rules:**
1. Anything that changes often sits below the cache boundary. A new message only appends to part 2.
2. A turn's tool calls and scratch work are thrown away after the turn; only outcomes are kept.
3. Anything not in the prompt is one tool call away (`recall`, `person`, `trip`); nothing is stuffed in "just in case".
4. **Long chats are folded.** The chat part has a budget (about 60,000 tokens). When a trip passes it, a smaller model folds the oldest chunk (about half) into **"the story so far"**: decisions, open threads, who cares about what, with message numbers as references. The fold runs in the background, right after Go posts once the chat passes its budget, or after a quiet minute (at most 10 minutes in a busy chat). The story has its own cap (about 5,000 tokens) and is rewritten from the old story plus the next chunk when the chat fills again. Recent messages stay word for word. Each fold costs one cache miss, so folds are rare and large.
5. **Nothing is lost:** every message stays in the trip log word for word, and `recall` finds it.
6. **Deletes are the exception to append-only:** a deleted message must vanish from Go's context, so a delete rebuilds part 2 from that point (one cache miss).
7. **Caps:** people's pages only for people in the current conversation; the record shows open and in-progress lines in full and decided or booked lines short; tasks only running plus the last few; tool results trimmed; a turn has a maximum number of steps.
8. **Safety net:** a sudden burst over budget before a fold is ready drops the oldest lines for that one turn and answers anyway.

Target: a prompt of 20,000 to 50,000 tokens, 85% or more cached, first word in about a second.

## 10. Tasks: big jobs on the trip's computer

### When a job becomes a task

The composer has no slow tools, so the only way to do slow work is `start_task`. A job is a task when it needs a website without an API, many steps, long reading or comparing, a form, or more than about 10 seconds. Booking and paying are never tasks (section 13). Watching something over time is a desk timer plus a cheap check, not a computer sitting open.

### A task's life

1. **Start.** `start_task(brief, returns)` saves a task row (id, trip, brief, the shape of the answer, the working card id, deadline) and posts a **working card** (`kind: working`, steps, `state: running`). The composer also says one short line ("On it. Looking for villas with a pool in North Goa.").
2. **Hand off.** The tasks layer sends the job to the trip's Bash through `/v1`: `POST /v1/conversations` (one per job, so the conversation is idle on `/v1` exactly when nothing of the job is left to run) and then a message with `hand_off: always` (the composer already decided; Vestra's own replying model is skipped), the brief as `message`, only the trip facts the job needs as `context` (treated as data, never instructions), the answer's shape as `output_schema`, and what "done" means as `success_criteria`. Go's memory and ixigo search reach the job through Go's MCP server (below).
3. **Progress.** `/v1` delivers the moments that must never be lost (`task.started`, `task.completed`, `task.failed`, `task.stopped`, `interaction.created`) as signed, retried webhooks, and keeps progress, which is frequent and stale within seconds, on the conversation's **live event stream** only (in Vestra's words: "too live or too chatty for a webhook"). So while a task runs, Go keeps that conversation's event stream open and gets the task's to-do list each time it changes (the stream carries the to-do list, questions, hand-offs and status, not each tool step); if the stream drops, Go reopens it from the last event number, and the webhooks still arrive regardless. Go updates **the same card in place** with `replace_card`: steps tick, and the screenshot thumbnail (`GET /v1/users/{id}/screenshot`, re-hosted by Go) refreshes only when the screen changed. At most one card update every 5 to 10 seconds. No pushes, no extra messages; "Go is typing..." is not used for tasks.
4. **Watch.** Tapping "Watch" sends `card_tap` to Go, which creates a fresh view session (`POST /v1/sessions`, `screen: view`) and answers with its link (`open`). A session link lasts 15 minutes, so Go never posts one in the chat; it mints a new one on every tap. "Stop" sends `card_tap`, and Go stops the job (`POST /v1/conversations/{id}/stop`).
5. **Needs someone.** `/v1` raises an interaction (`interaction.created` webhook):
   - a **question** ("which dates?"): Go asks the room and answers the interaction with the reply;
   - a **hand-off** (a login, a one-time code, a captcha): the card turns `needs_you` and is pinned for that person (push), Go says one line naming them, and either the person takes over from the Watch link (`screen: control`) or gives the code in the chat, which Go passes on as the interaction's answer;
   - a **tool call** or **approval** never appears, because Go's tools run without asking (below) and the job has no tools that need a yes.
6. **Done.** A message passed on while the job runs (`message_task`, with the job's `output_schema`) can run on `/v1` as a run of its own, before or after the job's start, and each run ends with its own `task.completed`. So a `task.completed` is one run ending; the job is done only when its conversation is idle and its task has ended, and the trip token stays live until then. The result lands on the desk. The next composer turn says it in Go's voice as a **new message** (an options card with three villas and "Put it to a vote"), and the working card turns to done and stays as a record of what Go did.
7. **Failed.** The card says "Didn't work"; Go says what went wrong in one line and offers to retry.

### Routing messages when there are many tasks

Every message goes to the composer first; tasks never read the chat. The composer picks one of five moves: answer directly; start a task; pass the message to a running task (`message_task`); stop a task; answer about a task from its progress. It knows which task because replies to and taps on a working card are exact; a task waiting on a person is checked first for that person's next message; otherwise it matches by meaning against the running tasks list (and Jev question 4 helps); if unclear, it asks, and it never guesses on anything that costs money.

**Limits:** at most 3 tasks run at once per trip (more wait on the desk); every task has a deadline; tasks never talk to each other, the composer connects their results.

**Over a long trip** (20 or 30 tasks): only running tasks and the last few finished ones sit in the prompt. A finished task's result moves into memory as facts or record lines and the task drops out, so task 25 costs no more than task 2.

**When things go wrong:** a lost webhook or a dropped stream cannot strand a task. A sweep every couple of minutes checks `GET /v1/conversations/{id}` (`status`, `open_work`, `open_interactions`) and `GET /v1/events` for anything missed. `/v1` is the source of truth for the job's status. A computer that is not up yet makes the task wait. Every task has a deadline and a spend cap (`limits.spend_per_task_usd`).

### The trip's computer, lean

The trip's Bash should do Go's jobs and nothing else: no personal connectors, none of Bash's "house" features, no memory of its own, no way to pay. What follows was read from Vestra's code on staging (`apps/server/src/platform`, `packages/shared/src/platform`), 5 October.

**Set up once, through `/v1` (no Bash change):**

| What | How |
|---|---|
| One user per trip | `POST /v1/users` (safe to repeat), then `POST /v1/users/{id}/warm`. At most 10 warms in flight per org and one per user per minute. |
| No memory of its own | `memory_mode: none` on the org (`PATCH /v1/org`). The `remember` tool disappears. |
| One deployment for every trip | A deployment `go-trip-task`, set as each trip user's `default_deployment`: the model, `limits.spend_per_task_usd` (say $2), `apps.allow: []`, and Go's task `instructions` (up to 8,000 characters, added after Bash's own core rules; they cannot replace them). |
| Go's tools, served by Go | **Go's MCP server** registered once with `POST /v1/mcp-servers`, with `Authorization: Bearer ${user_secret:TRIP_TOKEN}`. Every trip user reaches the same server, and the per-user secret (`PUT /v1/secrets/TRIP_TOKEN?user_id=`) says which trip is asking, so a job only ever sees its own trip. Go sets a fresh token when a task starts and revokes it when the task ends. The server offers `trip`, `person`, `recall`, `note` and ixigo's read-only search. Read tools carry `readOnlyHint`; `note` is listed in the deployment's `mcp_tool_policy` as `run_without_asking`. So the Bash calls Go directly, with no pause and no approval. (Function tools would pause the task and wait for Go to answer each call; the MCP server is simpler and faster.) |
| Caps | Per user day and month caps (`PATCH /v1/users/{id}`), org caps (`PATCH /v1/limits`). |
| Ending a trip | `PATCH /v1/users/{id} status: disabled` after the idle period; `DELETE` erases it (runs one at a time). |

**What `/v1` cannot do today, and the small Bash changes for it** (Bash is ours to change; each is a small, separate PR):

1. **Composio's app router reaches every user.** Each sandbox start opens a Composio session with all 800+ apps, and `apps.allow` does not stop it inside a task, so the job could ask to connect Gmail. **Change:** in `buildDispatchPlatform` (`apps/server/src/platform/deployments/dispatch-platform.ts`), add a `deny` rule for `mcp__composio__*` when the manifest's `apps.allow` is empty (the rule engine already matches globs).
2. **Bash's house tools cannot be switched off.** Installing abilities and MCP servers, other sessions, GitHub, app previews, paid media tools, sub-agents. **Change:** add `deny_tools: string[]` to `DeploymentManifest` (`packages/shared/src/platform/deployment.ts`), carry it in the task's platform context, filter the tool list in `buildNativeToolList` (`apps/sandbox/.../native-tools.ts`), and emit matching `deny` rules as a backstop. Go's deployment denies everything it does not need.
Not needed for the hackweek, later if the bench says so: a best-effort `task.progress` webhook (latest wins, no retries) if holding many streams gets heavy; built-in skills filtered by `manifest.skills` for company users; a lean base prompt profile for company tasks (Bash's long prompt stays today; Go's instructions sit after it).

**Paying is impossible by construction, not by instruction.** `/v1`'s `approvals.always` (payments, bookings, cancellations) is an instruction to the model on the browser path, not a system check. Go does not rely on it: the trip's Bash holds no card and no paying tool, never logs in to an account with saved payment methods (a login is a hand-off to the person, for sites without cards), and booking happens only in the composer through the vault (section 13).

**Limits to plan for:** `/v1` allows 60 requests a minute, 8 in flight and 20 open event streams per API key, and a turn needs $0.05 left in the org wallet. At most 3 tasks run per trip, so one key carries about 7 busy trips' streams; Go uses a small pool of keys and spreads streams across them. `/v1` is not public yet; Go is an internal customer.

## 11. Memory

Go's memory lives in **Go's own Postgres**, never in the sandbox and never in Vestra. What the group shares lives on the Server.

| Where | What |
|---|---|
| **Server** (shared truth) | The trip, messages, votes, bookings, money, and **the trip record** (decided, agreed, open, doing, booked). Go writes record lines through the socket and keeps a copy checked against the change number. |
| **Go's Postgres** | **The trip log** (every event and every Go action, in order, with proof), **people's facts** ("Priya: vegetarian", who said it and in which message, who may see it, history kept when a fact changes), Go's to-dos, tasks, desk items. |
| **The sandbox** | Nothing that lasts (`memory_mode: none`). |
| **The vault** | Cards and logins, under their own key. Never memory. |

**Pages are drawn, not written.** Each person's page is drawn from their facts: one line per fact, each with its proof. Go never keeps prose about a person that a model rewrote. That is why "forget me" is exact (delete the facts, the page redraws without them), every line has a source, changes are clean (a new fact replaces the old one, history underneath), and each fact can carry who may see it. A short summary on top of a long page may come later, written from the facts and thrown away when they change. Place pages (Go's know-how about stays and spots) come later, built the same way.

**Saving.** One way in: every save is an event in the trip log with proof. Jev flags candidates on each message; the after-turn pass proposes facts and record lines; code decides (the proof must point to a real message about the right person; "agreed" needs two yeses or the organizer, and a 👍 counts; private facts stay only for Go). Facts are keyed (`Priya · food`), so a new one replaces the old one by lookup, not by search.

**Finding.** While a trip is active, its working set (chat, record, pages, running tasks) sits in the service's memory: a composer turn reads it in about 20 ms. Searching older things is a Postgres word search over messages and facts, about 50 to 100 ms. Vectors only if replays show misses.

**Across trips.** A person keeps one `person_id` everywhere. Facts about their travel follow them only if carry-over is on. Another trip's chat never does.

**The sandbox's window into memory:** four tools on Go's MCP server (section 10): `trip()`, `person(name)` (group-visible facts only), `recall(question)` (this trip only), `note(fact, proof)` (a suggestion; Go's code checks it before it becomes a fact). Locked to one trip by the per-trip token, which Go sets when a task starts and revokes when it ends. Never private facts, contact details, budget answers or cards. Everything it reads is logged against the task.

## 12. The ixigo layer

ixigo gives Go travel search, status and booking through its MCP server. The layer sits between ixigo and everything that uses it:

| Kind | Used by | Rules |
|---|---|---|
| **Search** (flights, trains, buses, stays, places) | Composer (quick tools), tasks (read only, through Go) | Results cached per query for a few minutes; each result keeps `checked_at` so cards say "checked 3 min ago". |
| **Status** (flight status, PNR, availability, fares) | Watches | Scheduled, cheap, deduplicated; a change becomes a desk item. |
| **Booking** | Composer only, after the payment flow | Never exposed to the trip's computer. Every booking carries the spend approval's `approval_id` and is recorded with `add_booking`. |

- **Tool choice.** If ixigo exposes many tools, Jev picks the few a turn needs (the pattern from Bash's tool search: find, then run) instead of sending every schema.
- **The trip's computer** gets ixigo search through Go's MCP server (section 10), which only offers read kinds, so Go can log, cap and cache it. The Bash never talks to ixigo's MCP directly.
- **Prefetch** (stretch): Jev-confident searches start while the composer thinks.
- **To confirm with ixigo:** the MCP address and auth, the exact tool list and argument shapes, which tools book or change bookings, rate limits, sandbox versus live inventory, and refund and cancellation tools.

## 13. Money and the vault

A payment needs two separate approvals, and neither is Go's own word:

1. The group votes; the vote closes with a **mandate** (the choice, the cap, refundable only, who pays). The payer taps "Yes, book it" (a Server button).
2. Go checks the live price and asks the Server with `request_spend_approval`. The Server runs the spend check and signs a **one-use spend approval** (Ed25519, at most 10 minutes).
3. The payer taps Approve on Go's pay card; the App opens **Go's vault page** from a short-lived link.
4. The payer confirms with their **passkey** (WebAuthn: Face ID, Touch ID or fingerprint, or a phone over QR on a laptop). The vault checks the approval (signature, audience `go-vault`, not expired, not used, amount within the cap), then pays the booking hold through the payment rail with the payer's card. The card was added on Go's vault page through the payment processor's own form, so the processor holds the card number and the vault keeps only its token. Go then confirms the booking.
5. Go records the booking with the `approval_id` (the Server marks it used), records the expense, posts a ticket card, and replaces the pay card with its paid version.

**Rules:** the vault is its own store with its own key and lives on **Go's domain**, never the App's, so only Go's vault page can ask for the payer's passkey. The App opens it as its own page, never in a WebView or an iframe. This works the same for a Flutter app and a PWA: passkeys are a web standard, and an installed PWA opens Go's page in the phone's in-app browser sheet, where Face ID works. Cards never reach the model, the chat, logs or the trip's computer, and the vault itself never holds a card number (only the processor's token); the payer never types a CVV into Go and none is stored; only test cards until the card-on-file legal read. On iPhone, a PWA gets pushes only once it is on the home screen (iOS 16.4 and later), so the App should nudge people to install it. Test a real passkey payment on an iPhone PWA early in the week.

## 14. Calls

Go can call a business for the group (a hotel's late check-in, a cab). It says in the room who it will call and why, waits 30 seconds for anyone to say stop, then calls. A call card shows the call live and is updated in place; the outcome lands in the chat and, where it settles something, in the record. Calls never pay. The voice model hears the call with its own ears only (no second transcriber beside it), so the card shows Go's own lines and the outcome. This week Go calls only numbers on an allowlist. The call service's voice model and number are chosen during the build; the room behaviour above is fixed.

## 16. Failure and recovery

| What fails | What happens |
|---|---|
| The socket drops | The Server reconnects (1, 2, 5, 10, then 30 s); unanswered requests are resent with the same ids and done once. |
| An event is missed | The change-number gap triggers `read_trip` and `read_messages`. |
| A composer turn crashes | The desk item stays and the turn runs again; `request_id` keeps every write single. |
| Jev is slow or down | The composer decides as if Jev were not there. |
| The model is slow or down | "Go is typing..." stays honest for 10 s at a time; after a limit Go says it is having trouble and retries; the desk keeps the work. |
| A webhook from Vestra is lost | The sweep reads the job's status from `/v1` (`GET /v1/tasks/{id}`, `GET /v1/conversations/{id}`, `GET /v1/events`). |
| A task's event stream drops | Go reopens it from the last event number; the important moments also arrive as webhooks. |
| `/v1` rate limits | A small pool of API keys, with streams spread across them. |
| The trip's computer is not up | The task waits; setup's sweep keeps trying. |
| A fold misses something | Facts and record lines were saved with proof as they happened; `recall` finds the original message. |
| A payment step fails | Nothing is charged without both keys; the approval is released with `cancel_spend_approval`; Go says what happened. |
