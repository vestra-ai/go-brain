## 1. Auth, modes, scopes, idempotency, ids

**Header**: `Authorization: Bearer vk_live_<43 base64url>` or `Bearer vk_test_<43>` (`P/auth.ts:15-16`, regex `^vk_(live|test)_[A-Za-z0-9_-]{43}$`).
Missing → 401 `missing_api_key`; bad → 401 `invalid_api_key`; revoked → 401 `key_revoked`; expired → 401 `key_expired`; org off → 403 `org_disabled` (`P/auth.ts:52-131`). The org is the key's org (no org header for keys; `Vestra-Org` + `Vestra-Mode` are only for console JWT sessions, `P/auth.ts:99-122`).

**Test vs live** (`S/common.ts:3`): "A test key sees only test users, test deployments and test money." Partitioned by mode: users (`platform_org_users` keyed org+mode+external_id), conversations, secrets (company and user stores resolve in the user's mode), webhooks endpoints (an endpoint hears only its key's mode), wallet (`platform_org_wallets` per mode), idempotency keys, events. NOT partitioned: deployments (org-wide; test keys run `draft_version`, live keys run `live_version`, `P/deployments/resolve.ts:1-9,56-57`) and MCP servers (one row serves both modes, `P/abilities/mcp-servers.ts:107-110`).

**Key scopes** (`S/card.ts:13-22`; enforced `P/http/key-scopes.ts`, `P/plugin.ts:78-82` → 403 `scope_missing`). `KeyScope = 'all'|'runtime'|'setup'|'admin'`; a key made with no `scopes` is `all`. Per card line:
- `admin`: users (POST/PATCH/DELETE /v1/users*), keys, org (`PATCH /v1/org`), `PATCH /v1/limits`.
- `setup`: deployments, tests, secrets (`PUT/GET/DELETE /v1/secrets*`), MCP servers, webhooks (explicit `scope:'setup'` on every /v1/webhooks route).
- `runtime`: conversations, tasks, interactions, events stream, files, sessions, screenshot, `GET /v1/users`, `GET /v1/users/{id}`, `POST /v1/users/{id}/warm` (explicit runtime), memory, usage, `GET /v1/events`.
→ Go needs an `all` key (or `[runtime, setup, admin]`). Note `POST /v1/conversations` with a `user_id` creates the user on first use with only `runtime` scope (`P/http/scope.ts:47-57`).

**Idempotency** (`P/http/idempotency.ts:18-64`): header `Idempotency-Key`, 1-255 chars (else 400 `invalid_idempotency_key`), scoped per org+mode, kept 24 h. Same key + same body + same route → stored answer replayed; conversations routes also set `Idempotent-Replayed: true|false`. Same key, other body/route → 409 `idempotency_key_reused`. Same key while first still running → 409 `idempotency_in_progress` (an abandoned reservation frees after 5 min). 5xx/throw frees the key. Routes that use it (`await idempotent(` sites): POST users, conversations, messages, conversations stop, interactions answer/cancel, deployments create/versions/promote/rollback, files, connections, routines, batches, mcp-servers (via `abilities/http-helpers.ts:34`), webhook delivery retry. NOT idempotent by design (they return secrets/tokens): POST /v1/keys, /v1/sessions, /v1/webhooks (create, roll-secret), /v1/users/{id}/warm, PUT /v1/secrets. On `POST .../messages` the Idempotency-Key is also stored as the turn's `client_message_id` (unique per conversation, forever), so a retried send lands once (`P/conversations/routes.ts:95-104`, `send.ts:57-60`).

**Ids** (`S/ids.ts`): `org_ key_ conv_ task_ int_ file_ dep_ whk_ dlv_ evt_ con_ mcp_ skl_ nb_ rtn_ bat_ call_ ses_ turn_`. A user is named by YOUR id (`UserRef`, `S/users.ts:8`: `^[A-Za-z0-9][A-Za-z0-9._:@-]{0,127}$`).

**Every response** carries header `vestra-request-id: req_<32 hex>` (`P/http/request-id.ts`).

## 2. Users

### POST /v1/users — create or return existing (scope admin)
Body `UserCreateBody` (`S/users.ts:29-36`):
```ts
{ user_id: UserRef,            // required, your id
  name?: string(1..200), email?: email(≤320), locale?: string(2..35 BCP47),
  timezone?: string(1..64 IANA), metadata?: Record<string, unknown> }
```
Always **200** with `UserDetailView` (`P/users/routes.ts:20-28`). "Safe to repeat with the same user_id": an existing user is returned unchanged — the profile in a repeat is IGNORED (`P/users/provision.ts:59-60`); use PATCH to change it. Race-safe on unique (org, mode, external_id) (`provision.ts:48-116`; loser → may 409 `user_create_in_progress`). First creation emits webhook `user.created {user_id}`. Creating a user does NOT start a computer; the sandbox is created lazily on first work/warm.

`UserView` (`S/users.ts:39-59`): `id, object:'user', name|null, email|null, locale|null, timezone|null, metadata, status:'active'|'disabled', spend_cap_usd:number|null (daily), monthly_cap_usd:number|null, default_deployment:string|null (dep_…), memory_mode:'vestra'|'customer'|'none', is_service_user:boolean, created_at`.
`UserDetailView` adds (`S/users.ts:62-70`): `spend_today_usd, spend_month_usd, caps_remaining:{day_usd:number|null, month_usd:number|null}`.

### GET /v1/users (runtime), GET /v1/users/{user_id} (runtime) → `UserDetailView`
### PATCH /v1/users/{user_id} (admin) — `UserPatchBody` (`S/users.ts:73-91`), ≥1 field:
```ts
{ name?: string|null, email?: string|null, locale?: string|null, timezone?: string|null,
  metadata?: Record<string,unknown>,          // replaces
  spend_cap_usd?: CapUsd|null,                // per-day; null = company default per user
  monthly_cap_usd?: CapUsd|null,
  default_deployment?: string|null,           // id or slug; null = company default
  status?: 'active'|'disabled' }              // disabled → every call for them 403 user_disabled
```
`CapUsd` = `z.number().nonnegative().max(1_000_000)`, ≤2 decimals (`S/usage.ts:23-24`). A user cap above the company cap → 400 `cap_above_maximum`.
### DELETE /v1/users/{user_id} (admin) → **202** `{id, object:'user', deleted:false, status:'deleting'}`; erases computer, files, memory as a job; webhook `user.deleted {user_id, complete?}` when done (`P/users/routes.ts:52-58`, `P/users/delete.ts`). The `platform_org_users` row is removed, so the same `user_id` can be re-created after.

### POST /v1/users/{user_id}/warm (runtime; no Idempotency-Key)
`P/compute/routes.ts:11-15`, `P/compute/warm.ts:75-111`. User must exist (404 otherwise; it does NOT create). Response `{ user_id, status: 'ready'|'waking' }` with **200** when connected, **202** while waking. Limits: `MAX_WARMS_IN_FLIGHT_PER_ORG = 10` (per org+mode) → 429 `warm_limit` (no Retry-After header); `WARM_COOLDOWN_MS = 60_000` — a second warm within 60 s answers `waking` and rides the first. Refuses with 402 `wallet_empty` / `spend_cap_reached` and 403 `account_blocked`. Warm itself spends no credits.

### GET /v1/users/{user_id}/screenshot (runtime) → `image/jpeg` bytes, `cache-control: no-store`
`P/sessions/routes.ts:73-77`, `P/sessions/browser.ts:39-47`. 409 `browser_not_open` when Bash's browser is not running; 502 `screenshot_failed`; 5 s timeout. 1440×900.

## 4. Deployments

Routes (`P/contract/route-table.ts:176-190`; handlers `P/deployments/routes.ts:44-111`, `release-routes.ts`, `apply-routes.ts`): all `setup` scope.
- `POST /v1/deployments` → 201 `DeploymentObject`. Body `DeploymentCreateBody` (`S/deployments.ts:25-31`): `{ name: string(1..120), slug?: /^[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?$/, description?: ≤2000, manifest?: object, note?: ≤500 }`. Starts with a draft version.
- `POST /v1/deployments/{id_or_slug}/versions` → 201 `DeploymentVersionObject`; body `{ manifest: object, note? }` (`S/deployments.ts:43-46`). Moves `draft_version` (test keys run it).
- `POST /v1/deployments/{id}/versions/{n}/promote` (LIVE key only, else 403 `live_mode_required`) → `DeploymentPromoteResult`. Refused 409 `test_run_failed` if its latest run failed, 409 `test_run_required` if it has no passing run AND the deployment has ≥1 scenario; with zero scenarios it promotes (`P/deployments/promotion.ts:117-139`).
- `PUT /v1/deployments/{name}` applies a whole vestra.yaml as JSON (`?promote=after_tests|now|no`), returns `DeploymentApplyResult` (`S/deployments.ts:180-223`).
- `PATCH /v1/deployments/{id}` `{name?, description?, status?:'active'|'archived'}`.
- `DeploymentObject` (`S/deployments.ts:88-100`): `id, object, name, slug, description, base:'bash', status, draft_version:int, live_version:int|null, created_at, updated_at`.
- A live key on a deployment with no live version → 409 `deployment_not_live`; an org default with no version in the key's mode silently means plain Bash (`resolve.ts:39-57`). Test conversations pin the version they started on (`dep_x@n`); live ones follow the live pointer each message (`P/conversations/turn-context.ts:58-63`).

**DeploymentManifest** — `S/deployment.ts:79-114` (full):
```ts
export const DeploymentManifest = z.object({
  base: z.literal('bash').default('bash'),
  instructions: z.string().max(8000).default(''),
  language: z.string().default('auto'),

  approvals: z.object({ always: z.array(ApprovalCategory).default(['payment','booking','cancellation']) })
              .default({ always: ['payment','booking','cancellation'] }),
  model: z.string().default('default'),                         // or an id from GET /v1/models
  memory: z.object({ mode: MemoryMode.optional() }).default({}),
  notebooks: z.array(z.string()).default([]),                   // nb_ ids
  skills: z.array(z.string()).default([]),                      // skl_ ids or built-in names
  tools: z.array(ClientToolSpec).default([]),                   // functions YOUR code answers (tool_call)
  environment: EnvironmentSpec.optional(),                      // setup_script, env, repos, files
  routines: z.array(...).default([]),                           // NOT USED by a version
  limits: z.object({ spend_per_task_usd: z.number().positive().max(100).default(2) }).default({ spend_per_task_usd: 2 }),

```
- `ApprovalCategory = 'payment'|'booking'|'cancellation'|'send_email'|'publish'|'delete'` (`:7`). `MemoryMode = 'vestra'|'customer'|'none'` (`:8`).
- `ManifestMcpToolPolicy` (`:68-76`): `{ server: 'mcp_…', deny: ToolName[]≤200 = [], require_approval: ToolName[]≤200 = [], run_without_asking?: ToolName[]≤200 }`. ToolName = `/^[A-Za-z0-9_.-]{1,128}$/` (`S/common.ts:43`). A policy naming a server not in `mcp_servers` → 400 `mcp_server_not_listed` (`P/deployments/refs.ts:107-111`). Version policy only ADDS to the server floor (deny = union; ask = union minus deny).
- `ClientToolSpec` (`:11-30`): `{ name: /^(?!mcp__)[a-z][a-z0-9_]{0,63}$/, description: 1..1024, input_schema: {type:'object',…}, timeout_s: int 5..600 = 120, read_only?: boolean, run_without_asking?: boolean }`. Without `read_only`/`run_without_asking` true, a function waits for the person's yes before the call reaches you (`clientToolWaits`, `:38-40`). Names colliding with native tools → 400 `tool_name_reserved`.
- No `tools.native`/native-tool allow or deny list exists in the manifest today; `tools` is client functions only. Unknown manifest keys are stripped by zod (non-strict object), not rejected.
- `limits` is spend only (no time limit, by founder law). `apps.allow` is enforced ONLY at `POST /v1/connections` (`P/connections/links.ts:42` → 403 `app_not_allowed`); nothing at runtime (see §13).

**Default deployment**: per user via `PATCH /v1/users/{id} {default_deployment}`; per org via `PATCH /v1/org {default_deployment}`. A new conversation uses body `deployment` → user default → org default → none (plain Bash) (`P/conversations/routes.ts:52`, `create.ts userDefaultDeployment`, `resolve.ts:39-44`).

## 5. MCP servers and secrets

### POST /v1/mcp-servers (setup) → 201 `McpServer`
`CreateMcpServerBody` (`S/abilities.ts:93-101`, `.strict()`):
```ts
{ name: string(1..80),
  slug: /^[a-z][a-z0-9-]{0,39}$/,                 // what mcp_invoke names; rule prefix mcp__<slug>__<tool>
  url: url(≤2048) public https,
  auth: { type:'none' } | { type:'headers', headers: Record</^[A-Za-z0-9-]{1,64}$/, string(1..2048)> } | { type:'oauth' } // oauth → 400 oauth_not_available
       = { type:'none' },
  tools: { deny: ToolName[]≤200 = [], require_approval: ToolName[]≤200 = [] } }   // the floor; no allow list (strict → `allow` is 400)
```
- **No `transport` field**: stored as `{ transport: 'http', url, headers }` (streamable HTTP) (`P/abilities/mcp-servers.ts:33-55`).
- Templating: header values (and nothing in the URL — `${` in url → 400 `secret_in_url`) may contain `${secret:NAME}` (company store, key's mode) or `${user_secret:NAME}` (that user's store). Regex `/\$\{(secret|user_secret):([A-Z0-9_]+)\}/g` (`P/abilities/company-mcp-runtime.ts:18`). An auth-type header (e.g. Authorization) with no `${…}` ref → 400 `raw_secret_in_header` (`mcp-servers.ts:49-53`). ≤20 headers. Values are filled per user when the box loads its MCP list; a missing secret silently drops that server for that user (`unavailable: missing_secret`, `company-mcp-runtime.ts:63-76`) — so PUT the user secret BEFORE the user's first task.
- `McpServer` (`S/abilities.ts:116-134`): `object, id:'mcp_…', slug, name, url, auth{type, headers? (as written, refs not values)}, tools{deny, require_approval}, secrets: string[], user_secrets: string[], created_at, updated_at`.
- `POST /v1/mcp-servers/{id}/check` `{user_id?}` → `{object:'mcp_check', ok, tools: string[], reason?: 'missing_secret'|'auth_required'|'url_not_public'|'unreachable', missing?: string[]}` (`S/abilities.ts:147-157`).
- `GET /v1/mcp-servers/{id}/tools?user_id=` → page of `{object:'mcp_tool', name, denied, requires_approval}`.
- `PATCH` while a deployment's LIVE version uses the server with a test key → 409 `mcp_server_live`.

**Tool policy / readOnlyHint (the "company action" gate)**: every tool of a company MCP server asks the person's yes unless (a) the server's MCP listing marks it `readOnlyHint: true`, or (b) the version lists it in `mcp_tool_policy[].run_without_asking` (`packages/agent-sdk/src/policy/company-action.ts:1-37`). Deny rules still win (`mcp__<slug>__<tool>` deny/ask rules built in `P/abilities/tool-rules.ts:63-105`). The box reaches company servers through the `mcp_search` / `mcp_invoke` meta-tools (`apps/sandbox/src/harness/native-tools.ts:749-760`), which only exist when sandbox flag `ABILITY_MCP_V1` is on. An ask on a company tool reaches you as `interaction.created` type `approval`, whose yes MUST carry `present_user: true`.

### Secrets (setup) — `P/abilities/secrets.routes.ts`
- `PUT /v1/secrets/{NAME}` body `SecretPutBody` (`S/abilities.ts:20-25`, strict): `{ user_id?: UserRef, value: string(1..8192) }`. **`user_id` goes in the JSON body, not the query.** With `user_id` → that user's store (`${user_secret:NAME}`), name must match `/^[A-Z0-9_]{1,64}$/` (`S/users.ts:95`), and the user is created on first use. Without → company store, name `/^[A-Z][A-Z0-9_]{0,63}$/`. Response `Secret {object:'secret', name, user_id|null, mode}`. Storing again replaces. Never idempotent-stored.
- `DELETE /v1/secrets/{NAME}?user_id=…` → `{object:'secret', name, user_id, deleted:true}`; 404 `secret_not_found`.
- `GET /v1/secrets?user_id=…` → names only.

## 6. Conversations, messages, tasks

### POST /v1/conversations (runtime) → **201** `ConversationCreated`

```ts
{ user_id?: UserRef,            // created on first use; absent = company's own Bash (400 user_required if org require_user)

```
Response = `Conversation` + `turn_id?` (`S/conversations.ts:238-240`).

### POST /v1/conversations/{conversation_id}/messages (runtime) → **202** `ConversationTurn` (200 if `Prefer: wait` settled it)
`SendMessageBody` (`S/conversations.ts:54-88`, strict):
```ts
{ message: string(≤32000) = '',
  context?: Record<string, unknown>,                // rides a <job_context> fence, data only
  attachments?: { file_id: 'file_…' }[] (≤10),
  output_schema?: JSON Schema (≤32 KB),
  success_criteria?: string(1..4000),
  tools?: ClientToolSpec[] (≤32),                   // this message only, merged over the deployment's by name
  hand_off: 'auto'|'always' = 'auto',
  metadata?: ConversationMetadata,
  stream?: boolean }
```
**There is no `deployment` field on a message** — the deployment is fixed per conversation. Whole request body ≤ 100 KB (`MAX_BODY_BYTES`, `S/common.ts:37`).
- `hand_off: 'always'`: no model call; runs `create_task` directly with title from the message (`P/conversations/run-turn.ts:289-318`); reply text is exactly `"Started work on it."` (`HAND_OFF_SAY`, `run-turn.ts:50`). `task.started {task_id, title, turn_id}` is appended to the conversation stream (and as a webhook) after the task row exists and before dispatch (`run-turn.ts:66-82`).
- Response `ConversationTurn` (`S/conversations.ts:191-219`): `id:'turn_…', object:'conversation.turn', conversation_id, status:'running'|'working'|'requires_action'|'completed'|'failed'|'stopped', reply|null, answer|null, data|null, outcome:{met,reason}|null, work: {task_id, title|null, status:'queued'|'working'|'waiting'|'done'|'failed', result: string|null (≤280)}[], tool_calls: ConversationPendingToolCall[], error:{code,message}|null, created_at, finished_at|null`. At the 202 the hand-off usually has not created its task yet, so `work` may be empty: get the task id from `task.started` on the stream, or `GET /v1/conversations/{id}` `open_work`, or send with a short `Prefer: wait=N`.
- `Prefer: wait=N` (N ≤ 120, `MAX_WAIT_SECONDS`): holds until the turn AND its work end (statuses completed/failed/stopped/requires_action), polling 500 ms then 1.5 s; replies header `Preference-Applied: wait=N` (`P/conversations/wait.ts`, `routes.ts:107-113`). It holds one of the key's 8 in-flight slots the whole time.
- 409 `conversation_busy` while Bash is still writing a reply in this conversation (one composer turn at a time; stale after 10 min) (`send.ts:69-71`, `store.ts:55,108-118`). With hand_off always the busy window is only the create_task call; work running does NOT block a new send. 402 `wallet_empty` / `user_cap_reached` / `org_cap_reached` before anything is claimed (`send.ts:61-63`); the wallet needs ≥ $0.05 billed remainder (`MIN_TURN_RESERVE_USD`, `P/money/wallet.ts:16`).
- Error codes in `turn.error.code`: `output_invalid, work_lost, process_lost, credits_exhausted, model_timeout, tool_failed, bad_tool_args, loop_exhausted, unauthorized, internal` (`S/conversations.ts:211-216`).

### POST /v1/conversations/{id}/stop (runtime) → `{ id, object:'conversation.stop', stopped_work: task_id[] }` (`routes.ts:149-157`). `POST /v1/tasks/{task_id}/stop` stops one task.

### GET /v1/conversations/{id} (runtime or session token) → `Conversation` (`S/conversations.ts:157-189`)
`id, object:'conversation', user_id|null, deployment_id|null, deployment_version|null, status:'idle'|'replying'|'working'|'waiting', metadata, created_at, last_active_at, open_work: {task_id,title,status}[], open_interactions: {interaction_id:'int_…', task_id, kind: stored kind e.g. 'tool_permission'|'ask_question'|'composio_auth'}[], pending_tool_calls: {call_id, name, arguments, task_id|null}[], last_event_seq: int, cost_usd, cost_breakdown`. ## 7. The live event stream (SSE)

**Path**: `GET /v1/conversations/{conversation_id}/events` (key or session token) (`P/conversations/routes.ts:126-147`). Query `ConversationEventsQuery` (`S/conversations.ts:251-262`): `format: 'sse'|'json' = 'sse'`, `after?: int ≥0`, `limit: 1..500 = 100` (json only), `task_id?: 'task_…'` (filters `data.task_id === task_id`). `format=json` → `{ data: StreamEventObject[], next_after: int }` (poll-able page).
Also `stream: true` on POST conversations/messages answers that turn's events and ends when the turn settles (`P/conversations/stream-turn.ts`).

**Frame format** (`P/events/stream.ts:80-82`):
```
id: <seq>
event: <type>
data: {"seq":<n>,"type":"<type>","data":{...},"created_at":"<iso>"}

```
`data:` is the WHOLE event object (seq/type/data/created_at), not just `data`. Pings have no `id:` line: `event: ping` / `data: {"type":"ping","data":{},"created_at":…}`.
**Resume**: `Last-Event-ID: <seq>` header wins over `?after=<seq>` (`stream.ts:52-64`). Non-integer → 400 `invalid_last_event_id`. A seq older than retention or past the head → **410 `stream_expired`** (never a silent replay) (`stream.ts:66-70`); recover by reading `GET /v1/conversations/{id}` and following from `last_event_seq`. Retention: 30 days (`P/webhooks/reaper.ts:22`), keeping each live stream's newest row.
**Heartbeat**: ping every 15 s (`STREAM_PING_MS`); each ping re-checks the key and user; a revoked key / disabled user / ended session ends the stream with `event: error` `{code:'key_revoked'|'user_disabled'|'session_ended', message}` (`stream.ts:182-205`). SDKs treat 45 s of silence as dead. The server ends streams on deploy/shutdown; reconnect with Last-Event-ID. Server polls the table every 500 ms hot / 5 s idle.
**Limits**: 20 open streams per key (`MAX_OPEN_STREAMS`, `P/http/in-flight.ts:37`) → 429 `too_many_streams` (no Retry-After); session-token streams: 50 per org, 200 per process (`P/events/client-streams.ts:7-8`). A stream frees its in-flight slot once open.

**Event catalog** (`S/events.ts:8-25`): `message.delta, message.completed, task.started, task.progress, task.completed, task.failed, task.stopped, interaction.created, interaction.resolved, interaction.expired, screen.control, session.started, session.ended, file.created, routine.fired, usage.updated, usage.threshold_reached, usage.cap_reached, conversation.status, user.created, user.deleted, connection.completed, connection.failed, connection.removed, memory.observed, batch.completed, deployment.version_created, deployment.promoted, deployment.rolled_back, test_run.completed, key.created, key.revoked, error, ping`.

```ts
{ approve: boolean, present_user?: boolean, message?: string(1..500) /* with a no */, nonce?: string(1..4096) }
```

## 12. Rate limits and errors

- **60 requests/min per key**, fixed 60 s window, in process (single replica) → 429 `rate_limited` with `Retry-After: <secs to reset>` (`P/http/rate-limit.ts:11-28`, `P/plugin.ts:89-94`).
- **8 in flight per key** (16 for console) → 429 `too_many_in_flight`, `Retry-After: 1` (`P/http/in-flight.ts:11-16`, `plugin.ts:85-88`). Checked BEFORE the rate limit, so it does not spend the minute budget. A `Prefer: wait` send holds its slot up to 120 s.
- **20 open SSE streams per key** → 429 `too_many_streams` (no Retry-After). Session tokens: 50 streams/org.
- **Warm**: 10 waking per org+mode → 429 `warm_limit`; 60 s per-user cooldown.
- **Wallet minimum**: a turn needs ≥ $0.05 billed remaining (`MIN_TURN_RESERVE_USD`) → 402 `wallet_empty`. Caps → 402 `user_cap_reached` / `org_cap_reached` / `spend_cap_reached`.
- Per-task spend cap `limits.spend_per_task_usd` (default $2, max $100) stops work with `task.stopped reason:'max_budget'`.
- Body ≤ 100 KB → 400 `body_too_large`. Active-task cap per user 30 when `ACTIVE_TASK_CAP_V1` is on (`apps/server/src/services/task-capacity.service.ts:45`).
**Error body** (`S/common.ts:12-22`, built in `P/plugin.ts:121-135`):
```json
{ "error": { "type": "invalid_request|authentication|permission|not_found|conflict|rate_limited|cap_reached|upstream|internal",
             "code": "user_not_found", "message": "…", "param": "tools.0.input?", "names": ["…"]?, "deployments": ["…"]?,
             "request_id": "req_…" } }
```
Branch on `code`, never `message`. Status per type: 400/401/402/403/404/409/410/429/5xx. Full code list with remedies: `P/contract/errors.ts` (~250 codes). Retryable: 409 `idempotency_in_progress`, 429s, 503 `database_unavailable`/`auth_unavailable`, 502 `user_create_failed`.

## Gaps and surprises a builder will trip on

1. **Per-tool task steps are NOT on the conversation SSE stream.** Only todos, interactions, task start/end, files, usage and status are projected (`relay-tap.ts:220-222`). Live "what is it doing" needs polling `GET /v1/tasks/{id}/trace` (60 rpm budget) or relying on `task.progress.todos`. `task.progress` and `message.delta` are never webhooks.
2. **20 SSE streams per key** caps concurrent live trips per key. Options: several API keys, session-token streams (50 per org, but they hide money fields and tool_call events via `eventForCaller`, and live 15 min), or webhooks plus `GET /v1/conversations/{id}/events?format=json&after=` polling.
3. **No `deployment` on a message.** The deployment is chosen at `POST /v1/conversations` (or user/org default) and fixed for the conversation. Test conversations pin the version they started on.
4. **`PUT /v1/secrets/{NAME}` takes `user_id` in the JSON body**, not the query (DELETE/GET use the query). User-secret names allow a leading digit; company ones must start with A-Z.
5. **A missing `${user_secret:…}` silently drops the MCP server for that user** (no error to the API caller; the model just has no tools). PUT the secret before the first message; verify with `POST /v1/mcp-servers/{id}/check {user_id}`.
6. **Company MCP servers are org-wide and reach every company user's task**, not only the version's `mcp_servers` (`P/abilities/tool-rules.ts:99-100`), unless `VERSION_PINS_V1` pins them. On the box they are reached only via `mcp_search`/`mcp_invoke`, which need sandbox flag `ABILITY_MCP_V1`. Confirm both flags in the target env (registry defaults are false; values live in Railway/Blaxel env, not code).
7. **Every non-read-only Go MCP tool asks for a yes** (`interaction.created` type `approval`) unless the server sets `readOnlyHint: true` or the version lists it in `mcp_tool_policy[].run_without_asking` (and the server must also be in `mcp_servers`, else 400 `mcp_server_not_listed`). Answering it needs `present_user: true`.
8. **`apps.allow` is not enforced at runtime** (only on `POST /v1/connections`), hence change (a). Even `[]` leaves Composio tools in the catalog until change (b).
9. **`POST /v1/users` needs an admin-scoped key**, ignores profile fields on repeat, and returns 200 (not 201). Conversations/secrets/sessions with a `user_id` create the user implicitly (`user.created` webhook either way). `warm` and `screenshot` do NOT create; 404 for an unknown user.
10. **Live mode needs a promoted version**: a live key on a deployment with no `live_version` → 409 `deployment_not_live`; promote requires a passing test run only if the deployment has scenarios. An org default with no live version silently runs plain Bash.
11. **`screen: 'control'` 409s unless `BROWSER_SHARED_CONTROL` is on**; handoff interactions suggest `control`. Use `view` for Watch. Sessions last 15 min with no refresh; `frame_ancestors` empty unless `allowed_embed_origins` is set, so iframing fails by default.
12. **Human asks never expire on a live task** even though `expires_at` shows +10 min; only client `tool_call`s time out (`timeout_s`). Go must answer or cancel (`POST /v1/interactions/{id}/cancel`), or stop the task.
13. **The hand-off's task id is not in the 202 body** in most cases; take it from `task.started` (stream or webhook, carries `turn_id`) or `GET /v1/conversations/{id}.open_work`.
14. **409 `conversation_busy`** if two sends overlap during the composer's reply/create_task window; serialize sends per conversation and retry.
15. **`GET /v1/events` has no `conversation_id` filter** (only type/user_id/task_id/time/after), and the forward poll (`after=evt_`) returns `next_cursor: null` by design.
16. **SSE `data:` is the whole event object** (`{seq,type,data,created_at}`), not only the payload; ping frames have no `id:`. A stale Last-Event-ID returns **410**, not a replay.
17. **Rate limits are in-process on one replica**: during a deploy overlap they are approximate, and streams are force-closed on shutdown (reconnect with Last-Event-ID). `warm_limit` and `too_many_streams` carry no Retry-After.
18. **Webhook deliveries are not ordered** and can arrive minutes apart on retry (1/5/15/60 min, 5 tries). Dedupe on `evt_` id; `vestra-webhook-id` (dlv_) is per endpoint.
19. Open reds touching this surface (from project memory, not re-verified here): `approvals.always` is not system-enforced on every path unless `APPROVALS_GATE_V1`; skills/knowledge/MCP servers are not versioned unless `VERSION_PINS_V1`; MCP connect DNS rebinding (`mcp-client.ts`); company MCP header secrets are resolved into the box's MCP config (values reach the sandbox).
